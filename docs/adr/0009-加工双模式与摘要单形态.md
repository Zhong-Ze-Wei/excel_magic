# 0009 — 加工双模式与摘要单形态

**日期**: 2026-07-01
**状态**: 已采纳
**分支**: feat/analysis-hub-dual-mode（阶段 1-3）
**前置**: [0007 — 功能区入口收敛](./0007-功能区入口收敛.md)

## 背景

ADR 0007 把功能区收敛为「清洗 / 智能加工 / 摘要」三个入口。其中清洗已在更早版本实现了 Hub 双模式（CleaningHub + OptimizeView/CleaningView，共享 `rulesConfig`）。加工和摘要仍是单视图（AnalysisView 940 行 / SummaryView 493 行）。

本次需决策：**加工和摘要是否也该做双模式？底层怎么统一？**

## 决策

**加工对齐清洗的 Hub 双模式；摘要保持单形态。**

### 判断依据：是否有「可调规则参数」

| 模块 | 核心可调参数 | 适合双模式 | 结论 |
|------|------------|----------|------|
| 清洗 | `rulesConfig`（11 种原子规则开关） | ✅ | 已是 Hub 双模式 |
| 加工 | `labelingPlan.outputColumns`（输出列定义） | ✅ | 本次改为 Hub 双模式 |
| 摘要 | 无（`analysisTheme` 是 prompt 描述，非结构化规则） | ❌ | 保持单形态 |

核心原则：**双模式只有存在"可调规则参数"时才有意义**。摘要本质是 prompt→文本，没有规则参数可供专家模式细调，强行套 Hub 会造空壳。

### 加工双模式复用清洗范式

```
AnalysisHub（壳：顶部切换横条 + v-if/v-else，不持有数据逻辑）
  ├── AnalysisSimpleView（简易：模板快选 + AI 生成 + 一键打标）
  └── AnalysisView（专家：outputColumns 手编 + 高级 Prompt + 完整审计）
        ↓ 共用（单一真源）
  dataShare.labelingPlan（共享方案，切换零迁移）
  composables/useLabeling（共享打标引擎）
  services/labelingPlan.js（共享校验/规范化）
  components/analysis/EditColumnDialog（共享列编辑弹窗）
```

**切换零迁移的设计精髓**：`labelingPlan` 提升到 dataShare store 作单一真源。简易模式 AI/模板写入它，专家模式手编写入它，两模式是同一对象的不同编辑器，切换时无需任何数据搬运（与清洗的 `rulesConfig` 共享完全对称）。

## 备选方案

### A. 三个模块都做双模式（否决）
- 摘要没有规则参数，专家模式没有可编辑对象，会造空壳 UI
- 违背"形式追随内容"原则

### B. 都不做双模式，保持单视图（否决）
- 加工的 AnalysisView 已 940 行，模板/手编配置平铺，新用户门槛高
- 简易模式（模板驱动）能显著降低加工的使用门槛

### C. 加工双模式 + 摘要保持单形态（采纳）
- 加工有 outputColumns 天然适合双模式
- 摘要诚实保持单形态，不为了"统一"而过度抽象

- ❌ processMode 不在设置 UI 暴露切换（切换在 Hub 里，与 cleaningMode 一致）
