# 代码结构

项目保持 Vue + Pinia + Vite 的纯前端架构，构建产物为静态页面。文件处理和业务编排在浏览器执行，AI 请求由浏览器直接发送到用户配置的平台。“AI 模块独立”指代码职责独立，不代表新增服务端或后台常驻任务。

## 目录与职责

```text
app/src/
├── main.js / App.vue       应用启动、布局选择、全局意图弹窗
├── router/                页面路由
├── views/                 页面交互与展示
├── components/            通用组件、业务组件、桌面与移动端布局
├── composables/           Vue 状态、生命周期和业务流程的组合
├── stores/                跨页面共享状态及设置
├── services/
│   ├── ai.js              兼容入口：读取设置，调用独立 AI 模块
│   ├── ai/client.js       接收显式配置，执行普通/流式 HTTP 请求
│   ├── ai/batch.js        接收任务执行函数，处理并发、结果和进度
│   ├── prompts.js         提示词兼容入口，集中导出
│   ├── prompts/           按业务划分的提示词与预设
│   ├── excel.js           FileReader 读取、文件校验、导出下载
│   ├── excel/workbook.js  字节解码、Sheet 解析、工作簿构建
│   └── 其他业务服务        清洗、列画像、打标方案、分组统计等
├── data/demoData.js        内置示例表格
├── config/                平台配置与默认清洗规则
├── styles/                全局样式与设计变量
└── __tests__/             业务规则与服务契约测试
```

现有调用方继续通过 `services/ai.js`、`services/prompts.js` 和 `services/excel.js` 使用原接口。拆分不需要批量修改页面导入路径。

## 页面与共享状态

路由使用 Hash 模式，桌面和移动端共用业务逻辑，通过不同布局和页面模板呈现。

| 路径 | 页面 | 职责 |
|------|------|------|
| `/` | HomeView | 文件上传、数据集意图和四个业务模块的入口 |
| `/cleaning` | CleaningHub | 简易模式 OptimizeView / 专家模式 CleaningView |
| `/process` | AnalysisHub | 简易模式 AnalysisSimpleView / 专家模式 AnalysisView，共享打标方案 |
| `/summary` | SummaryView | 列画像、主题配置和 AI 流式摘要 |
| `/aggregate` | AggregateView | 分组求和、均值、计数、最小值和最大值 |
| `/analysis`、`/optimize` | 重定向 | 分别转到 `/process`、`/cleaning` |

| Store | 保存的内容 |
|-------|------------|
| `dataShare` | 表头、数据行、来源、核心列、打标方案与结果、任务说明、Sheet 信息和原始 File 对象 |
| `importIntent` | 上传后任务目标、核心列、选中的模块、AI 建议、预规划方案及弹窗状态 |
| `settings` | API 平台、密钥、模型、清洗规则、并发数、自动意图分析开关和简易/专家模式 |

表格和意图主要是会话内状态。设置中的配置项写入 localStorage；设置弹窗状态、最近一次 AI 优化时间等临时状态不持久化。当前没有任务数据库或自动恢复机制。

## AI 与提示词边界

`ai.js` 从 Pinia 获取配置，交给 `ai/client.js` 发送请求；批处理由 `ai/batch.js` 调度，单次任务执行函数由调用方提供。后两个模块不导入 Vue、Pinia 或 localStorage，可以在 Node 测试中直接加载。HTTP 客户端仍依赖运行环境提供 `fetch` 等 Web API。

`ai.js` 保留 `callAI`、`callStreamingAI`、`callAIBatch`、`testConnection`、`createSemaphore`。批处理仍在每个任务实际开始请求时读取设置；普通请求和流式请求原有的模型选择、system prompt 策略、参数、错误文案均保留。

| 提示词文件 | 内容 |
|------------|------|
| `context.js` | 数据集任务说明与当前步骤的上下文 |
| `intent.js` | 核心列识别、导入意图分析 |
| `cleaning.js` | 智能清洗规则生成 |
| `labeling.js` | 打标方案生成、执行提示词编译、从提示词还原方案 |
| `summary.js` | 分析主题与数据摘要 |
| `presets.js` | 预设模板及方案创建，复用 labeling 的编译函数 |
| `capabilities.js` | 各业务模块的能力约束 |

这里仅拆分原 `prompts.js` 中的模板；`pipelinePlanner.js` 等编排代码中的局部提示词仍在原处。

## 文件处理与业务引擎

`excel.js` 负责浏览器文件边界，`excel/workbook.js` 只处理传入的字节、工作簿和表格数据，不读取文件、不触发下载。`DEMO_DATA` 移到 `data/demoData.js`，仍从 `excel.js` 导出以兼容调用方。

导入保持现有 UTF-8 / BOM / GBK 处理规则。`readFile` 校验扩展名并拒绝空表；`readSheet` 保留不同的校验及错误文案，不能为了去重而将两者强行统一。

| 服务 | 职责 |
|------|------|
| `cleaningRules.js` | 原子规则、自定义规则、清洗判定管道 |
| `dataProfiler.js` | 列类型识别、统计画像、分层抽样和 AI 统计文本 |
| `labelingPlan.js` | 打标方案规范化与校验、行结果规范化 |
| `groupAggregate.js` | 分组统计和结果表格生成 |
| `jsonParser.js` | AI JSON 输出解析 |
| `intentAnalysis.js` | 构建表格快照、调用 AI 推断意图、规范化建议 |
| `pipelinePlanner.js` | 按任务目标规划清洗、加工、摘要和分组对比的配置 |
| `toast.js` | Vue 通知状态与通知方法 |

`services` 并非全部都是纯函数：意图分析、方案规划仍负责调用 AI，通知服务依赖 Vue。判断模块能否独立测试，应看实际依赖。

## Vue 业务组合

| Composable | 职责 |
|------------|------|
| `useFileUpload` | 文件读取、写入共享数据、打开意图弹窗、上传状态与错误提示 |
| `useGlobalDataSync` | 页面挂载和共享表格变化时复制数据到页面，并提供导入、断开操作 |
| `useCleaningPipeline` | 清洗预览、统计与导出数据组织 |
| `useLabeling` | 批量打标、进度与结果回写 |
| `useExport` | 页面导出流程 |
| `useShare` | 共享处理结果与跳转 |
| `useDevice` | 响应式设备尺寸判断 |

后续新增业务逻辑时，优先复用这些边界：组件负责用户交互，composable 负责响应式流程，不需要页面状态的计算放在业务服务中。不要仅为缩短文件增加无业务含义的中转层。

## 验证方式

在 `app/` 目录执行 `npm test` 和 `npm run build`。

| 测试 | 覆盖重点 |
|------|----------|
| `aiClient.test.js` | 模拟 HTTP 请求参数、错误、流式回调、旧入口兼容、逐任务读取设置 |
| `aiBatch.test.js` | 信号量并发、单任务失败后继续执行、结果和进度 |
| `prompts.test.js` | 意图分层、六种输出类型、预设及摘要契约 |
| `excel.test.js` | 多 Sheet、CSV 编码、空表和缺失 Sheet、错误、导出数据、无 DOM 的编解码 |
| `cleaningRules.test.js` | 清洗规则与管道 |
| `dataProfiler.test.js` | 列画像与抽样 |
| `labelingPlan.test.js` | 方案与结果规范化 |
| `groupAggregate.test.js` | 分组统计 |
| `jsonParser.test.js` | JSON 容错解析 |
| `toast.test.js` | 通知生命周期 |

这些测试不调用真实 AI 平台。结构拆分时还对原提示词和新模块做了 31 组输出对照。构建通过不代表真实模型输出稳定，也不代表后台运行或大文件性能已经验证。

## 后续整理顺序

1. **统一设置默认值与持久化入口**：模型默认值在初始化和重置中重复；设置弹窗还直接读取 localStorage。整理时保留“编辑草稿，保存后生效”的交互及旧配置迁移行为。
2. **按流程提取页面逻辑**：优先整理摘要生成、方案生成等独立流程，继续复用现有 composable。简易/专家模式的交互差异不宜强行合并。
3. **明确数据生命周期**：梳理共享原始数据、页面副本、加工结果的归属和失效时机，再评估减少复制；这涉及行为，另开任务验证。
4. **按实测处理性能**：先测大文件解析、画像、渲染中的耗时和内存，再决定是否使用 Worker 或表格虚拟化。拆文件本身不会自动提高运行速度。

AI 的连续限流调度、流式事件跨网络分片解析仍沿用旧实现，需单独修复与回归测试，不属于此次结构整理的完成项。架构决策见 [ADR 0011](adr/0011-纯前端服务边界与兼容入口.md)。
