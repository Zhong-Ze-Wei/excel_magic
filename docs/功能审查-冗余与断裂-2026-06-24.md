# 功能审查 — 冗余与断裂

> 日期: 2026-06-24
> 基于: master 分支，commit `78e76ee`
> 范围: 6 个核心页面（首页/数据优化/数据清洗/批量翻译/数据分析/数据摘要）

## 背景

项目经历多轮迭代（v0.0.1 → v0.0.2 → 数据洞察 → AI 优化页），功能逐步膨胀。审查发现：部分功能存在职责重叠，部分模块间数据流断裂。本文档记录问题与建议，作为后续重构的依据。

## 当前页面职责

| 路由 | 页面 | 一句话定位 |
|------|------|-----------|
| `/` | HomeView | 上传入口 + 数据洞察卡片 + 模块推荐 |
| `/optimize` | OptimizeView | AI 一句话清洗端到端 |
| `/cleaning` | CleaningView | 规则配置清洗，三态审计 |
| `/translate` | TranslateView | 整列批量翻译 |
| `/analysis` | AnalysisView | AI 打标，新增分析列 |
| `/summary` | SummaryView | 列画像 + AI 流式报告 |

## 一、真冗余：HomeView 列分组概览 vs SummaryView 统计

### 问题

HomeView 的"数据洞察"里有一块"列分组概览"，和 SummaryView 的列画像统计高度重复：

| 维度 | HomeView 列分组概览 | SummaryView |
|------|---------------------|-------------|
| 底层引擎 | `computeAllProfiles` | `computeAllProfiles` |
| 数据量 | 前 50 行预览 | 全量 |
| AI 报告 | 无（除非切 AI 模式） | 流式生成完整报告 |
| 定位 | 迷你分析 | 唯一完整报告出口 |

两者都算列画像、推核心列、展示列类型分布。用户在首页看到的概览，到了摘要页会再看一遍。

### 建议

首页砍掉"列分组概览"块。首页只保留两个能力：
- **核心列推荐**（启发式 + 可手动切换）
- **模块推荐**（基于数据特征推路由）

首页定位为**路由分发器**，不是迷你分析页。完整的统计分析留给 SummaryView。

> ✅ **已解决（2026-06-25）**: 整个「数据洞察」区块已被移除，包括列分组概览和模块推荐。首页改为「数据集意图卡」+ 3 大功能卡片，用户通过 ImportIntentModal 显式选择任务。核心列推荐也改为用户在弹窗中手动指定，不再启发式猜测。

## 二、假冗余：OptimizeView vs CleaningView

### 看着像重复，其实边界清晰

两者共享同一个 `runCleaningPipeline` 引擎（`services/cleaningRules.js`），但交互模式和产出完全不同：

| 维度 | OptimizeView | CleaningView |
|------|-------------|-------------|
| 用户画像 | 不懂规则的小白 | 需要审计的专家 |
| 输入 | 自然语言一句话 | 手动勾选规则开关 + 调参 |
| 配置存储 | 局部 ref `aiRulesConfig`，用完即弃 | 全局 `settings.rulesConfig`，持久化 |
| 决策粒度 | suspect 直接降级为 delete | 保留 keep/delete/suspect 三态 |
| 可复现 | 不可（刷新即失） | 可（配置跨会话保留 + JSON 导入导出） |

**结论**：不是重复。OptimizeView 是 CleaningView 的"AI 加速器前端"，后端共享同一个 pipeline。

### 真问题：配置无法传递

OptimizeView 生成的 AI 配置是孤岛。用户觉得 AI 方案不错，想继续在 CleaningView 精调——做不到。OptimizeView 的按钮只有 `shareDataTo('/analysis')` 和 `shareDataTo('/summary')`，跳不了 `/cleaning`。

**建议**：OptimizeView 增加「在清洗页精调此方案」按钮，将 `aiRulesConfig` 写入 `settings.rulesConfig` 后跳转 `/cleaning`。

> ✅ **完全解决（2026-06-26）**: CleaningHub 统一入口 + OptimizeView 的 `aiRulesConfig` 改为 `computed from settings.rulesConfig`，两个模式共享同一份规则，模式切换无缝衔接（专家模式调规则 → 切回简易模式立即反映）。详见 [adr/0007](adr/0007-功能区入口收敛.md)。

## 三、功能断裂：数据流没接通

### P0：Optimize → Cleaning 配置无法传递（最严重）

见上一节。AI 生成的优质规则配置无法沉淀到全局 `settings.rulesConfig`。

### P1：打标结果只有 SummaryView 消费

`dataShare.labelingResults`（AnalysisView 产出）只有 SummaryView 读取。打标产出的标签列无法回流到清洗管道当筛选维度。

**场景断裂**：用户在 AnalysisView 打标了"情感：正面/负面"，然后想在 CleaningView 筛"只保留负面评论"——做不到，因为 CleaningView 不读 labelingResults。

**建议**：让 labelingResults 的 outputColumn 可作为 CleaningView 的自定义规则维度（参考 `columnEquals` / 值分布筛选）。

> ⚠️ **仍开放（2026-06-25）**: 打标结果（labelingResults）仍只被 SummaryView 消费。CleaningHub 的两个模式都不读 labelingResults，标签列无法作为清洗筛选维度。

### P1：Translate 翻译结果混入 rows，下游无法区分

TranslateView 翻译完成后，直接在全局 `rows` 末尾追加"翻译结果"列并覆盖。下游模块（Cleaning/Analysis）不知道哪列是原文、哪列是翻译。

**建议**：翻译列的元信息（列名、对应原文列索引）应记录到 dataShare 的某个字段，让下游可选"对翻译列还是原文列操作"。

> ✅ **部分解决（2026-06-25）**: dataShare 新增 `translatedColumns` 字段 + `addTranslatedColumn(originalIdx, translatedIdx, name)` action，已记录翻译列元信息。翻译合并进 AnalysisView 后走打标流程，结果统一存 labelingResults。但下游模块（CleaningHub）仍未消费 translatedColumns 来区分原文/翻译列。

### P2：SummaryView 交叉分析已被禁用

`computeCrossTabs` 函数仍在调用，但 UI 用 `v-if="false"` 注释掉了交叉分析入口（SummaryView.vue 第 177 行）。要么恢复 UI，要么删掉 `computeCrossTabs` 调用，避免跑空逻辑。

## 四、其他观察

### AnalysisView 参考列 vs dataShare.coreColumn

关系清晰但单向：
- `coreColumn`：全局单选，所有模块共享，UI 是 select
- AnalysisView `selectedInputColumns`：多选 checkbox，初始值 = `[coreColumn]`

**断裂**：AnalysisView 跑完打标后，`setLabelingResults` 写入全局，但 coreColumn 不更新。若用户在 Analysis 改了参考列，Home/Optimize/Cleaning 的 coreColumn 仍是旧值。

**建议**：Analysis 启动打标时，若 `selectedInputColumns.length === 1`，同步回写 `dataShare.setCoreColumn`。

### HomeView 模块推荐

有价值——解决"5 个功能页我该先用哪个"的决策疲劳。但 `recommendations` 只取前 3 条（`slice(0,3)`），数据特征丰富时可能漏掉真正该用的模块。

> ✅ **已废弃（2026-06-25）**: 模块推荐机制整体移除。首页改用 ImportIntentModal 让用户显式选择任务（clean/process/summary），不再靠启发式推荐。`recommendedRoutes` 变量保留但置空（注释标注「保留 class 逻辑兼容性」）。
